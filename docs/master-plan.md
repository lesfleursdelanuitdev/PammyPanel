## 0. The goal

**The panel is a Supabase-like platform that works with both Postgres and MariaDB** (momolig,
2026-10-06). Everything Supabase gives one Postgres project, the panel gives every **project** it
manages (Files, Code, Installed, Connected), over any number of databases, on either engine, and
through `connections` over external stores too. Supabase itself was not installed: it is one
Postgres database per stack and cannot use MariaDB.

**The namespace is the project and the domain**: a project's **Backend tab** answers at
`/_api/` on each of its own addresses (`https://tutorlumi.com/_api/v1/main/sessions`), with
`https://api.<domain>/v1/<project>/…` as the fallback.

| Supabase | In the panel | Postgres | MariaDB | Where |
|---|---|---|---|---|
| Database + Table editor | the Studio | live | live | studio-plan |
| SQL editor | **none, on purpose** (G-Q1) | — | — | — |
| Auth | a project's Backend users (B3, B7, B8) | B3 | B3 | backend-plan |
| Data API | `/_api/v1/<db>/<table>`, PostgREST-like (B2) | B2 | B2 | backend-plan |
| Row-level security | policies enforced in the service (B4) | B4 | B4 (no RLS in MariaDB) | backend-plan |
| Realtime | over the panel's row events (B5, C5) | B5 | B5 | backend-plan |
| Storage | buckets on local disk or S3 (ST) | — | — | storage-plan |
| Edge Functions | Code projects (8b) | — | — | phase8b-plan |
| Branching | dev branch databases (8b-5), Neon branches (X3) | yes | 8b-5 | |
| Backups | nightly dumps; **off-server copies (R1, live) and restore drills (R2-R3)**; restore from the panel (R4) | | | recovery-plan, Track R |
| Logs and metrics | Activity, Events, project logs, gauges and alerts (Track O) | | | |
| Client | `@lfdln/client` + `<pammy-*>` Lit components | | | backend-plan |

**Rule for the goal**: anything built for databases works on both engines and is tested on both
(Track T), unless the step says why it can't, and then the Studio shows the difference.

## 3. Rules every step is checked against

1. **A module's tables are its own**; others use its functions, ops or events. The boundary test
   checks table names in SQL against owners, as it checks imports.
2. **Each package has a public entry**, not `"./*"`.
3. **The kernel, the gate host and the sites name no module.**
4. **Sites only compose**: no SQL, no module logic.
5. **Runtime dependencies are declared** (socket ops and gate ops count).
6. **Registries are open**: no CHECK lists or fixed columns per module.
7. **Events carry the publisher's prefix** (`monitoring.check.down`, not `services.service.down`).
8. **Size and copies**: no new file over ~400 lines / 25 KB; no new copied block over 6 meaningful
   lines; allow lists only shrink (the copy check runs as a report until K is done).
9. **Shared server / browser code lives in `<package>/src/shared/`.**
10. **One release per step**: build, install, verify (both sites when shared code changes), "as
    built" written, this file updated.
11. **Release safety** (section 7).
12. **Security review**: steps marked 🔒 (S1, S2, B1's keys, B3, B4, B6, ST4, X2, U7) are reviewed
    by a second session before install, and by monadelanuit where possible; their tests are
    written first (T3 for those after it; S1 and S6 brought their own tests, before T3 existed).
13. **Test tiers** (Track T): fast tier on every commit (it includes the engine suites, T2-Q1),
    full tier before every install; a step that touches databases runs its suite on both engines.
14. **Both engines**: see section 0.
15. **A module works with only its must-haves**; everything else lights up when present (`worksWith`), tested both ways (modular-use-plan).
16. **A module's plugins plug into its sockets; the module names none of them** (rule 3, one level down).
17. **No untrusted project or PHP route on a host whose visitors sign in** for something else
    (S1e review F2: S1e keeps the gate's cookie from an app's server, but a page's own
    JavaScript on the same host can still use or plant it). Until S1e-Q3 is settled, the panel
    and its people place untrusted code on hosts of its own.

## 6. Branch and merge policy

- **`main` is the integration branch; `~/pamela-setup` stays on `main`** (other sessions merge
  there). Every step is built in its own worktree and merged when installed and verified.
- **At most one structural refactor open at a time** (C1, K-a, K-b, K-rename, C2, and Track U's
  U2, U3, U9). While K-a or
  K-b is open, `core/src/gate/**`, `packages/gate/**` and `packages/areas/**` are frozen for other
  work, and Code-project work pauses or stays inside `packages/projects/`.
- **Rebase daily** onto `main`; a rename lands with its codemod committed, so other branches
  rebase by running it.
- **Worktree hygiene**: a merged step's worktree is removed (2026-10-08: momolig approved removing
  the merged ones still open, `-backends`, `-c1`, `-k0`, `-modular`, `-r1`, `-s1`, `-s1b`, `-s1d`,
  `-s1e`, `-s6`; momolig does it).
- **Plans**: on `main` since the end of Track D (`backends-plan` merged).

## 7. Release safety

- **Expand, then contract**: a migration only adds; what is no longer used is removed in a later
  release, so the release before still works on the new schema and a rollback is just "install
  the previous release".
- **Side by side first**: anything that replaces a live mechanism (the deletion poller → outbox,
  `record_touches` → events, the gate's decision moving modules) runs beside the old one for a
  release, with both results compared (as 8-7a did for pammy.org's routing).
- **Every step's plan says how to roll it back**, and verify checks the rollback in a throwaway
  install where it can.
- **Pamela's smoke list** in pammy.org's verify: her pages, a protected folder sign-in, a form
  answer, a comment, the media API, WordPress at blog.pammy.org, File Explorer. A step that
  changes pammy.org's behaviour may keep pammy.org **one release behind** until it has run on
  lfdln for a day.
- **Install window**: momolig's choice, never during a known busy time for Pamela.
